## 3. 调查边界与方法

只检查了仓库内受控的导入、备份、导出、数据和日志根目录，以及仓库文档中
已经明确记录的原始导出包候选位置。对候选位置只做精确存在性检查，没有列举
候选位置所在的私人目录，也没有扫描整个磁盘。

调查包括：

- 初始 ChatGPT 导入解析器和随导入包保存的历史版本；
- 增量 ChatGPT 导入器；
- 资产目录创建逻辑；
- 初始处理数据库、当前数据库和 10 个已知历史数据库快照；
- 已保留的处理后导入包 ZIP 中央目录；
- 已保留处理包和解包副本的一致性；
- 受控根目录中的 ZIP、`.dat` 和 SQLite 家族文件计数；
- Git 历史中的 `.dat` 和 ZIP 路径计数；
- DB、WAL、SHM 的审计前后大小、时间戳和 SHA-256。

没有访问附件 URL，没有网络请求，没有整体解压 ZIP，没有读取或输出消息正文，
也没有输出私人文件名、完整附件 ID、完整本机路径、私人 URL、Tailnet 或认证
信息。

## 4. 来源审计

### 4.1 当前保留的处理包

受控范围内只有一个 ZIP。其中央目录有 11 个文件，类型仅包括 CSV、数据库、
JSONL、Markdown、PowerShell、Python 和 SQL：

- `.dat` 条目：0；
- 原始会话 JSON：0；
- `chat.html`：不存在；
- 原始资产映射清单：不存在；
- 处理后数据库：1；
- ZIP 条目与已解包副本逐项哈希一致：11/11。

该 ZIP 是处理后的导入成果包，不是原始 ChatGPT 导出包，不能作为附件实体源。

### 4.2 原始导出包的历史证据

保留的导入说明明确记载，初始原始导出结构曾包含：

- 分片会话 JSON；
- `chat.html`；
- 附件 `.dat` 条目；
- 原始资产映射清单。

初始导入器会读取资产映射清单，并从 ZIP 中读取每个资产条目的
`ZipInfo.file_size`。当前 172 条资产目录记录都有源 ZIP 条目大小。因此可以
确认：初始导入当时，原始 ZIP 中至少有 172 个可被枚举的实体条目。

但是，已知原始导出包候选位置当前均不存在；受控导入、备份、导出、数据和日志
根目录内也没有 `.dat`。所以只能证明这些条目历史上存在，不能证明其字节仍在
本机。

### 4.3 资产 locator 的原始语义

资产目录中的 locator 是资产清单键，即原始 ZIP 内的相对条目名。其关系形式为：

```text
attachment identity -> <attachment identity>.dat -> ZIP entry
```

它不是外部 URL，也不是当前磁盘上的绝对路径。初始导入器把该相对条目名、
原始显示名和 ZIP 条目大小写入资产目录及数据库，但没有把实体字节复制到处理
输出目录。

### 4.4 暂存、备份和历史

- 当前保留的解包目录是处理成果目录，没有实体。
- 已知备份是数据库和日志备份，没有实体 ZIP 或 `.dat`。
- Git 历史没有 `.dat` 或 ZIP 对象。
- 未发现可验证的内容哈希映射。
- 172 条目录记录保留相对条目名、原始名和源 ZIP 条目大小；报告不输出这些
  私人值。
- 940 条缺目录记录仍有附件关系元数据，其中一部分有源库标识或非 URL 来源
  标记，但这不足以证明实体字节存在。

## 6. 940 与 172 的阶段成因

数据库时间线如下：

| 阶段 | 会话 | 消息 | 附件元数据 | 资产目录 |
|---|---:|---:|---:|---:|
| 初始处理结果 | 177 | 5,229 | 348 | 172 |
| 增量前历史快照 | 178 | 5,917 | 348 | 172 |
| 当前 | 409 | 16,324 | 1,112 | 172 |

由此得到：

1. 初始 348 条附件中，172 条建立了资产目录映射，176 条没有映射。
2. 增量导入新增 764 条附件元数据，但资产目录仍为 172 条。
3. 当前 940 条缺资产目录记录正好等于：
   `176 + 764 = 940`。
4. 10 个已知历史数据库快照的资产目录内容摘要与当前完全一致，说明 172 条
   目录记录不是后续丢失；后续阶段从未补建资产目录。
5. 当前 172 条 `entity_missing` 的直接原因是：目录元数据仍在，但允许的实体
   根目录中不存在对应字节。

## 8. 导入器是否丢弃字节

结论分两段：

1. **初始导入：是，处理成果只保存资产元数据。**
   导入器读取原始资产清单和 ZIP 条目大小，写入资产目录 CSV 与 SQLite，但
   没有把 `.dat` 实体复制到输出。历史导入说明也明确把资产目录定义为映射表，
   不复制附件本体。

2. **增量导入：资产处理流程整体缺失。**
   增量导入器加载会话并写入会话、消息，不调用资产加载逻辑，不写资产表，也
   不复制实体。因此对新增 764 条只能认定“未清点资产”，不能认定每条实体都
   曾存在。

没有证据表明导入器发出外部请求或从临时 URL 下载附件。

## 10. 未来安全恢复计划

以下仅是未来计划，本节点没有执行：

1. **来源登记**
   对用户提供的原始 ZIP 只读计算 SHA-256、大小和中央目录清单；不整体解压。
2. **边界校验**
   拒绝绝对路径、路径穿越、设备名、符号链接和受控根目录逃逸；不接受临时
   URL 或网络下载。
3. **映射规则**
   优先使用原始资产清单建立
   `attachment identity -> archive entry` 精确映射；源库标识只能作为辅助证据，
   不能单独决定映射。
4. **实体校验**
   流式计算哈希，比较 ZIP 条目大小、附件声明大小、MIME、文件头、扩展名及
   会话/消息关系；不把私人标识写入公开报告。
5. **冲突处理**
   13 条冲突和所有多候选记录进入隔离清单，不自动选择、不覆盖、不猜测。
6. **审批清单**
   输出精确可恢复、可能可恢复、仅元数据、冲突和拒绝记录的脱敏计数，在人工
   审批前停止。
7. **原子复制**
   审批后才把通过校验的实体流式写入新的版本化暂存目录，逐文件校验后对整个
   新目录做同卷原子改名；不得覆盖现有导入目录。
8. **回滚**
   回滚只移除本次新建的版本化恢复目录和对应派生清单；现有导入成果和 SQLite
   不参与回滚。
9. **数据库策略**
   不修改当前 SQLite。映射和恢复状态先保存为独立、可重建、只读派生索引；
   是否进入正式数据库必须另立节点和迁移审批。
